# 服务器运维纪要

## 使用说明

本文件是服务器运维会话的初始化上下文和持续维护纪要，不是要求用户再次说明“发生了哪些变化”的问卷。

当本提示词被调用时，AI 必须先完整读取“纪要内容”，将其作为当前服务器环境的已知基线，然后继续处理用户接下来的运维任务。

- 如果用户只调用本提示词、没有附带其他任务，表示仅初始化运维上下文。AI 不得追问“本次有什么变化”，也不得要求用户重新提供纪要中已经存在的信息；只需简短确认纪要已经加载，可以开始运维。
- 除非用户明确要求“显示纪要”“查看纪要”或“展示内容”，否则不要在会话中完整复述本文件。
- 纪要中的信息用于减少重复查询，但不能替代对高风险操作所需的即时验证。当实时状态、用户当前说明或命令结果与纪要冲突时，以经过验证的最新状态为准，并更新纪要。

## 纪要源与持久化

本纪要的唯一真实来源是 `prompt-call` 当前加载的 Prompt 源文件：

- MCP Server：`prompt-call`
- Prompt：`server-maintenance-summary`
- Path：`prompts/server-maintenance-summary.md`

不要依赖旧的 `my-prompt` 仓库或某台电脑上的固定绝对路径。运维过程中产生需要长期保留的新增、修改或删除信息时，应针对 `prompt-call` 实际加载的上述 Prompt 源文件准备候选更新。

任何远程更新都必须先经过用户审计和明确批准，具体流程如下：

1. 重新读取远程文件及其当前 SHA，并基于最新内容生成候选版本。
2. 在会话中先展示变更摘要，分别列出 `ADD`、`DELETE`、`UPDATE`、`MERGE`；没有内容的类别可以省略。
3. 随后展示统一 Diff。新增行以 `+` 表示，删除行以 `-` 表示，并提供足够的上下文让用户判断变更位置和含义。
4. 明确询问用户是否批准本次更新。此时不得调用任何远程写入或删除工具。
5. 只有用户在看到当前版本 Diff 后明确回复 `OK`、`确认更新`、`批准写入` 等同等含义的指令，才视为批准。沉默、继续讨论、模糊表态或此前对其他操作的授权都不构成批准。
6. 如果用户拒绝、要求修改或没有批准，本次候选更新默认不生效。根据反馈修改后，必须重新展示完整的新 Diff 并再次请求批准。
7. 获得批准后、实际写入前，必须再次读取 Prompt 源文件。如果文件内容与生成 Diff 时不同，原批准立即失效；必须基于最新版本重新合并、重新展示 Diff 并再次获得批准。
8. 文件未变化时，使用当前客户端可用的受控文件编辑能力写入用户批准的完整候选内容。写入后重新读取文件进行验证，再报告更新结果。

只允许把已经实际执行并验证成功的结果纳入候选更新。计划、猜测、失败操作和未经确认的状态不得写入纪要。

`prompt-call` 本身只负责读取和调用 Prompt，不提供写入工具。如果当前客户端没有 Prompt 源文件写入权限或没有文件更新工具，必须明确说明本次变化尚未持久化，不得声称已经更新成功；仍可展示候选 Diff 供用户审计。

## 纪要目的说明

本纪要同时供 AI 和人阅读，用于描述服务器当前轮廓、重要历史调整、文件与配置位置、部署方式、Docker 镜像、网络入口以及关键安全约束。它的目标是让后续 AI 能快速进入运维状态，避免对已经明确且仍然有效的信息反复查询。

## 纪要规范

AI 在整个运维会话中持续跟踪已经执行并验证的变化，并遵守以下规范：

1. 开始工作前先整体读取现有纪要，理解当前服务器环境和既有约束。
2. 不要求用户手工汇总变化。AI 应根据本次会话中自己执行的命令、修改的配置以及验证结果，自动识别需要记录的变化。
3. 只记录会影响后续运维判断、访问方式、安全边界、服务部署、关键配置、数据位置、备份恢复或故障排查效率的信息；临时命令、无状态查询和容易重新获得的普通信息不记录。
4. 每条纪要应说明：做了什么、最终状态是什么、产生什么影响、为什么这样做，以及必要的文件路径、端口、服务名或配置位置。
5. 新增事项应写入最合适的现有分类并按顺序编号；不要因为是新内容就机械追加到文件末尾。
6. 对已有配置的调整，应直接更新对应旧纪要，使其反映当前最终方案；必要时简要保留对理解现状有价值的变更背景。
7. 已删除或已失效的规则、配置和服务，应删除或改写旧记录，不能让过时信息继续表现为当前有效状态。
8. 在写回前再次检查整份纪要，消除重复、冲突和已经失效的描述。
9. 不得在纪要中记录密码、Token、私钥、完整连接密钥或其他秘密信息。
10. 必须先展示候选 Diff 并获得用户对该 Diff 的明确批准，禁止自动写回。Prompt 源文件写入并验证成功后才能表示“纪要已更新”，并简短说明更新了哪个部分；默认不展示整份纪要。

## 纪要内容

### 安全层面

#### 1. SSH 登录安全加固

- 新增日常运维管理员账号 `adminops`，加入 `sudo` 管理组，可通过 `sudo -i` 获取 root 管理权限。
- 保留 root 账号登录能力，SSH 最终配置为允许 root 登录及密码认证；登录入口由网络访问控制保护，不再直接暴露公网 SSH。
- root 已配置 SSH 密钥认证，保留密钥登录作为管理和应急入口。
- 已验证 `adminops` 可正常登录、执行 sudo，并可切换至 root 身份。

#### 2. SSH 防暴力破解

- 安装并启用 Fail2ban，服务已设置为开机自动启动。
- SSH 防护规则：10 分钟内密码验证失败 5 次，封禁来源 IP 30 分钟。
- 最终参数：`maxretry=5`、`findtime=10m`、`bantime=30m`，日志读取后端为 `systemd`。

#### 3. 阿里云安全组收敛

- 删除公网 SSH TCP 22 入方向规则，公网地址 `118.178.229.176:22` 已无法直接连接。
- 删除无实际服务监听的公网 RDP TCP 3389 入方向规则。
- OpenVPN 隧道入口使用默认 UDP 1194，删除误建的 TCP 1194 规则。
- 保留 OpenVPN Web 管理与用户门户 TCP 943，以及网站所需的 HTTP/HTTPS 公网入口。
- 当前内部工具的公网 HTTP 入口为：Jenkins TCP 8080、Nacos TCP 8081、Windmill TCP 8082。
- SSH、MySQL 和 Nacos 服务 API 仍通过 VPN 访问主私网 IP `172.20.105.210`。

#### 4. OpenVPN Access Server 部署

- 使用 Docker Compose 部署 OpenVPN Access Server，镜像为 `openvpn/openvpn-as:latest`。
- 部署目录为 `/opt/openvpn-as`，持久化数据目录为 `/opt/openvpn-as/data`。
- 使用应用默认端口：TCP 943 提供 Web 管理及用户门户，UDP 1194 提供 VPN 隧道。
- VPN 公网接入地址为 `118.178.229.176`，管理页面为 `https://118.178.229.176:943/admin/`。
- VPN 设置为分流访问，仅发布单台主机资源 `172.20.105.210/32`，不接管用户的全部互联网流量。
- Windows OpenVPN Connect 已连接成功，客户端获得 VPN 地址 `172.27.224.2`。
- 已验证 VPN 建立后可访问主私网 IP `172.20.105.210` 的 SSH 22 和 MySQL 3306 端口。
- 当前使用未激活许可证的免费额度，支持 2 个并发 VPN 连接。

#### 5. MySQL 改为 VPN 私网访问

- MySQL Docker 端口绑定由 `127.0.0.1:3306:3306` 调整为 `172.20.105.210:3306:3306`。
- MySQL 容器已重新创建，主机仅在主私网 IP `172.20.105.210:3306` 提供连接。
- 阿里云安全组未开放公网 3306，MySQL 不对公网暴露。
- Navicat 已改为直接连接 `172.20.105.210:3306`，不再使用 SSH 隧道，并已测试连接成功。

#### 6. 最终访问策略

- 私网管理：连接 OpenVPN 后，通过 `172.20.105.210` 访问 SSH、MySQL，以及 Nacos API 8848/9848。

- 公网工具入口：Jenkins 使用 `http://118.178.229.176:8080`，Nacos 使用 `http://118.178.229.176:8081`，Windmill 使用 `http://118.178.229.176:8082`。

- 项目站点端口约定：10000 及以上端口用于项目站点，并要求配置 HTTPS；内部工具不占用该端口段。

- 后续新增 Oracle、PostgreSQL 等管理型服务时，应将服务端口绑定到 `172.20.105.210`，不在阿里云安全组开放公网数据库端口；现有 `172.20.105.210/32` VPN 资源规则无需重复添加。

### 配置中心与内部工具

#### 1. Nacos 配置中心

- 使用 Docker Compose 部署 Nacos `3.2.3`，部署目录为 `/opt/nacos`，运行模式为 standalone，使用内嵌存储。
- Nacos Console 映射为公网 `0.0.0.0:8081 -> 8080`。
- Nacos 服务 API 仅绑定私网：`172.20.105.210:8848` 和 `172.20.105.210:9848`。
- 持久化目录为 `/opt/nacos/data` 和 `/opt/nacos/logs`；鉴权密钥保存在权限为 `600` 的 `/opt/nacos/.env`，纪要不记录具体值。
- JVM 设置为 XMS 512 MB、XMX 768 MB；容器内存上限 1536 MB、CPU 上限 1.5、PID 上限 512。
- Docker JSON 日志轮转设置为单文件 10 MB、保留 3 个文件；Tomcat access log 已关闭。
- 已验证容器成功启动，日志显示 standalone embedded storage 启动成功。

#### 2. jobs-py 集中配置

- Nacos `public` 命名空间中已创建 `jobs-py-dev.toml` 和 `jobs-py-prod.toml`，Group 均为 `JOBS_PY`，格式为 TOML。
- 两份配置集中保存对应环境的 MySQL host、port、database、user、passwd 和 SSL 设置；纪要不记录具体密码。
- 创建 Nacos 程序账号 `nacosUser`，绑定 `ROLE_READER`，配置为读取 `public` 命名空间；已验证该账号可登录并读取两份配置。
- Windows 本地使用 Credential Manager 普通凭据 `jobs-py/nacos` 保存 Nacos 启动凭据，不在代码、本地配置文件或环境变量中保存密码。
- `jobs-py` 已改为根据 dev/prod 从 Nacos 读取对应 TOML；本地已验证 Nacos 登录、配置解析及 MySQL `SELECT 1`，结果为 `mysql_connection_ok=true`。

#### 3. Windmill Web 入口迁移

- Windmill Web 入口由 `https://118.178.229.176:10000` 迁移为 `http://118.178.229.176:8082`。
- Windmill Base URL 和 GitHub OAuth 回调地址已同步修改为 8082，GitHub 授权登录已验证成功。
- Nginx 配置文件为 `/opt/nginx/conf.d/windmill.conf`，Compose 文件为 `/opt/nginx/docker-compose.yml`。
- 已删除 Nginx 的 10000 SSL 监听及 Compose 的 `10000:10000` 映射；`nginx -t` 验证成功，主机已确认不再监听 10000。
- Jenkins Web 继续使用公网 HTTP 8080，不做调整。
